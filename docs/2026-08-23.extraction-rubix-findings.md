## Per-finding evidence

### 1. No remote / no onboarding

- `git -C ~/create/skills/rubix-review remote -v` returned empty on 2026-08-23 (verified during the review).
- loop-stack's README documents a clone-and-override onboarding block for ringer but nothing for rubix-review.
- The extraction plan's appendix draws `jroethel/rubix-review` on GitHub being cloned to fresh hosts; no task
  created that remote.
- Status: the user is creating the remote; the README onboarding block remains open.

### 2. Fail-closed dead end

- `loop-stack/skills/loop-review/SKILL.md` (contract section) and `loop-stack/skills/loop-drive/SKILL.md`
  say "stop and report that rubix-review must be installed and loop-stack's install.sh re-run" - no clone URL,
  no path, no literal command.
- `loop-stack/install.sh:213-215` (the no-installer WARNING) names `LOOP_STACK_RUBIX_ROOT` but not how to
  populate it.
- The operator persona most likely to hit this (fresh host, non-author) is the one least equipped to derive
  the recovery.

### 3. Drift guard weakness

- `loop-stack/install.sh:191-194` `_clauses_ok()` greps three fixed phrases; a contract with those phrases
  plus injected extra instructions wires cleanly. The contract text is pasted verbatim into reviewer
  subagent prompts, so injected text reaches the reviewers.
- `loop-stack/tests/gates/reviewer-contract.sh:55-66` (check 5) probes exactly two hardcoded roots
  (`$HOME/.agents/skills`, `$HOME/.claude/skills`) and skip-with-notes when unresolved - which is precisely
  the fresh-host case, and any host using the supported `RUBIX_INSTALL_DIR`/`AGENTS_SKILLS`/`SKILLS_DIR`
  overrides.

### 4. Copy-mode degradation

- `loop-stack/install.sh:204-205`: where symlinks are unavailable the contract is `cp`'d with only a printed
  "re-run install.sh after any contract change".
- A stale copy that still carries the three clauses passes `_clauses_ok` and gate check 5 forever; the suite
  is structurally blind to copy staleness. WSL/Windows filesystems (the owner's work environment) are the
  copy path.

### 5. Unvalidated rm -rf

- `install.sh:31` in this repo: `rm -rf "$DEST"` runs unconditionally before BOTH install branches (not just
  the copy fallback), where `DEST="$INSTALL_DIR/rubix-review"` and
  `INSTALL_DIR="${RUBIX_INSTALL_DIR:-$HOME/.agents/skills}"` (lines 9-10).
- The empty-var case is already safe: `:-` substitutes the default when the override is empty or unset.
- The open case: a relative or mistyped `RUBIX_INSTALL_DIR` (e.g. set from a broken host.env resolution in a
  caller) makes `rm -rf` fire on an unintended location. The fixed `/rubix-review` suffix bounds the blast
  radius but does not eliminate it.

### 6. rubix-autorun enum drift

- The brief describes a binary: present means offered, auto-run only when the config default is on
  ("off by default"). The shipped key (`loop-stack/config/repo-state.md`, template legend) is a three-value
  enum where `ask` is the default and `off` now means skip-silently - a mode the brief never described.
- Functionally the shipped default matches the brief's intent; the token `off` changed meaning between the
  two documents with no mapping note anywhere. The terminal Standards review independently flagged that
  `rubix-autorun` also has no doctrine paragraph in loop-stack `config/conventions.md` "Committed keys",
  unlike `autonomy-default` and `tracker`.

### 7. Caller-named env var

- `install.sh:5,33` in this repo: the copy-force override is `LOOP_STACK_FORCE_COPY`, in a repo whose stated
  contract is zero loop-stack dependency (SKILL.md must not reference loop-stack; the installer name leaks
  it instead). Any future non-loop-stack consumer inherits the misnomer.

### 8. No uninstall

- The loop-stack self-heal (`loop-stack/install.sh:186-188`) materializes this skill into the operator's
  skills home and wires two consumer symlinks; removing loop-stack later leaves the orphaned install plus
  two dangling `references/` symlinks. Nothing documents or automates the cleanup.

### 9. Plan task ordering

- The extraction plan presents tasks as 1, 2, 4, 5, 3, 6 (wave order) while its preamble says "execute in
  dependency order"; nothing warns a sequential reader that the jump 5 -> 3 is intentional.
  Owned by loop-stack's plan document, recorded here only because this pass surfaced it.
